# ADR-0005: Migrate HCIS Authentication to SQ Identity Without Migrating Credentials

**Status:** ACCEPTED
**Date:** 2026-08-27

## Context
HCIS currently owns authentication internally:
- `accounts` stores email, status, `password_hash`, MFA secret material, and principal type;
- `auth_sessions` stores hashed HCIS session tokens;
- `auth_recovery_codes` stores recovery-code hashes;
- `auth_audit_events` stores authentication events;
- login is email + password, with custom TOTP/recovery-code handling;
- HCIS role assignments reference `accounts.id`.

The existing password format is HCIS-specific scrypt. MFA secrets are also HCIS-owned. Importing these credentials into Keycloak would require custom compatibility code/provider behavior and would create long-term security/upgrade coupling.

HCIS is not yet in production, so preserving existing passwords is not a product requirement.

## Decision
Migrate **identity linkage and authorization continuity**, but **do not migrate HCIS password hashes, MFA secrets, recovery codes, or login sessions** into Keycloak.

Users create new SQ Identity credentials through Keycloak activation/reset flows.

## Preserve HCIS local principal IDs
Existing `accounts.id` remains the HCIS-local principal identifier during migration so existing references such as `account_role_assignments.account_id` do not need a disruptive rewrite.

Add an external identity mapping to the local principal, conceptually:
```text
accounts
  id                    <- existing HCIS local principal ID
  employee_id
  principal_type
  status
  identity_issuer       <- new
  identity_subject      <- new opaque Keycloak/OIDC sub
  email                 <- contact/profile snapshot, not identity key
```

The pair `(identity_issuer, identity_subject)` must be unique when populated.

Do not join or authorize by email/NIP after OIDC callback.

A future authorization-domain refactor may rename `accounts` to a clearer principal concept, but this migration does not require that refactor.

## Login identifier mapping
For migrated Employee accounts:
- Keycloak username = HCIS `employees.employee_number` (NIP) when available;
- Keycloak email = validated `accounts.email`, because every current HCIS account already requires an email;
- `employees.email` is treated as a comparison/profile source during migration; if it differs materially from `accounts.email`, migration reports the mismatch for explicit resolution instead of guessing;
- email login may be enabled as alternate login when unique and verified.

For non-Employee Staff that do not have NIP, use verified unique email as username during Foundation v1.

NIK is never provisioned as a login username.

## Credential migration
Do **not** import:
- HCIS `password_hash`;
- HCIS encrypted TOTP secret;
- HCIS recovery codes;
- HCIS session tokens.

At activation/cutover:
- Staff sets a new Keycloak password;
- privileged Staff configures new MFA in Keycloak;
- recovery codes are generated by Keycloak where required.

This deliberately avoids a custom Keycloak password-hash SPI or credential bridge.

## Authorization continuity
Keycloak does not replace HCIS authorization.

After OIDC authentication:
1. HCIS resolves local account by `issuer + sub`;
2. HCIS confirms the local account/domain state permits use;
3. existing HCIS role/permission/scope resolution continues using local `accounts.id`;
4. SQ Hub Application Access determines whether the identity may enter HCIS.

Existing HCIS `principal_type`, roles, permissions, and scopes remain HCIS-owned during this migration.

## OIDC application pattern
HCIS becomes an OIDC client of SQ Identity/Keycloak using Authorization Code flow.

Preferred browser architecture:
```text
Browser
  -> HCIS /auth/login
  -> redirect SQ Identity
  -> Keycloak authentication
  -> HCIS server-side callback/code exchange
  -> map issuer+sub to local account
  -> create HCIS-scoped HttpOnly application session
  -> existing HCIS authorization
```

Tokens are not stored in browser localStorage/sessionStorage.

HCIS may retain a local application-session mechanism, but that session becomes derived from OIDC authentication rather than a direct HCIS password login.

## Cutover strategy: controlled switch, not production dual-auth
Implementation may temporarily support an `AUTH_MODE`-style rollout flag in staging/controlled deployment:
- `local` = existing HCIS authentication;
- `oidc` = SQ Identity authentication.

Production must not expose both direct local-password login and OIDC login as parallel user-facing authentication paths after cutover.

Local credential material may be retained for a **maximum 14-day rollback window** after successful production cutover, while direct local login endpoints remain disabled externally.

After the rollback window and successful acceptance checks:
- irreversibly clear/remove HCIS password hashes;
- clear/remove HCIS MFA secret material;
- remove HCIS recovery-code data;
- remove/deprecate direct password-login and MFA-setup endpoints;
- remove obsolete crypto/auth implementation that is no longer needed;
- retain audit history according to retention policy, excluding unnecessary secret material.

After credential cleanup, rollback means restoring/recovering SQ Identity/Keycloak, not re-enabling custom HCIS authentication.

## Application Access prerequisite
Before HCIS production cutover, every migrated Staff identity that should use HCIS must have an explicit HCIS Application Access grant in SQ Hub.

Do not use Keycloak realm/client roles as a hidden substitute for the SQ Hub Application Access source of truth.

## Lifecycle boundary
HCIS account status is **domain-local state** and must not silently become global SQ Identity lifecycle state.

Initial migration rule:
- eligible `active` HCIS account -> candidate for HCIS Application Access after identity activation;
- HCIS `suspended` / `inactive` -> deny/revoke HCIS Application Access and/or local HCIS authorization, **not automatically disable the global Keycloak identity**;
- `invited` -> provision with required activation actions or hold pending according to the migration runbook;
- global Keycloak disablement is performed only when the Staff identity lifecycle owner determines the person should no longer authenticate to any SQ application.

Example: a Staff member may lose HCIS access but still legitimately need SPMB Admin or another application. HCIS is not allowed to disable that person's global identity merely because its local account is suspended.

The migration must report ambiguous/missing employee/email/NIP mapping rather than guessing.

## Rollback
Before irreversible credential cleanup, rollback may switch HCIS back to local auth only if:
- the issue is critical and OIDC cannot be restored promptly;
- the old credential tables/code remain intact;
- rollback has been rehearsed in staging;
- rollback is explicitly approved and audited.

No automatic silent fallback from OIDC failure to local password login is allowed.

## Consequences
- Existing role assignments do not need to be recreated because local `accounts.id` is preserved.
- Users must create new SQ Identity credentials once.
- Old HCIS MFA enrollment is intentionally discarded and privileged users enroll again.
- Migration implementation is simpler and safer than maintaining legacy credential compatibility inside Keycloak.
- HCIS authentication code can be deleted after a short verified rollback window.
- A later application can reuse the same SQ Identity without inheriting HCIS credential tables.
- Domain-local suspension cannot accidentally lock a Staff member out of unrelated SQ applications.
